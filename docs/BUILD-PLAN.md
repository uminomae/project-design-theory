# 構築の方針

2026-11-07 に始めた。

## 何をしているか

今までの四つのサイト（プロジェクトデザイン論・創造とは・欠損駆動思考・意識とは）を、今の状態のまま複製してこの repo に移し、ここで更新していく。一から作り直さない（pjdhiro 2026-11-07「今の状態をコピーするように複製し、そこを更新する」・`stance.md` 2-5。2026-11-10 に、退けられた読み「一から組み直す」のままだったこの行を直した）。

- 今までの repo（project-design・creation-space・kesson-space・awareness-space）は材料として読む。調査結果はそのまま写さない（下の「材料の扱い」）。サイトのファイルは、今の状態のまま複製して移した（下の項目）。
- 今までのサイトは、中身を持たず、新しい場所への転送だけにした（2026-11-07。下の項目と「進み具合」。始めは、新しいサイトが育つまで新旧を同時に公開しておく予定だった）。
- プロジェクトデザイン論のサイトは、今の状態をそのまま複製し、ここで更新していく。リンクと読み物だけのシンプルなサイトなので、すぐにできる。複製を公開したら、今までのサイトから転送リンクを貼る。見た目と作り方も今のまま継ぐ。（pjdhiro 2026-11-07）
- 今までの repo の更新は、四つとも止める。プロジェクトデザイン論のサイトに直しがあるときは、この repo で行う。（pjdhiro 2026-11-07）
- 複製は一歩ずつ進める。まずプロジェクトデザイン論のサイト（ポータル、次に読み物）。次に意識とは（awareness-space）など、ほかのサイトも順に移して、repo を一つにまとめる。一歩ずつ移すことで、無駄や重複に気づける。（pjdhiro 2026-11-07）
- 移す理由：今までの repo は、非公開の情報が git の履歴に入ってしまった。中身を新しい repo に移し、今までの repo は名前を変えて見えないところに残す。（pjdhiro 2026-11-07）
- 四つの repo（project-design・creation-space・awareness-space・kesson-space）を、この repo の一つの git でまとめて扱う。repo ごとに `pd/`・`cs/`・`as/`・`ks/` に分けて入れる。一つの論として明確になる。原典の PDF（creation-space の `knowledge/raw/` など）は git に入れず、手元だけで、この repo のディレクトリの中に置く（`.gitignore` で外す）。原典を除けば、まとめても 200MB ほど。（pjdhiro 2026-11-07）
- 手元の置き方の最終形：この repo（`~/dev/pd/project-design-theory/`）の中に `pd/`・`cs/`・`as/`・`ks/` がある。原典の PDF も、この中の git の外に置く。今までの四つの repo は名前を変えて非公開にし、手元では `~/dev/` の外に置く（`~/dev/` には公開の repo だけを置く）。`~/dev/` 直下の移行用のリンクは、移し終えたら外す。（pjdhiro 2026-11-07。2026-11-07 にこの形になり、リンクも外した）
- 今までの公開ページ（`uminomae.github.io/project-design/` ほか四つ）は、転送元として残す。中身は持たず、新しい場所へのリンクと転送だけのシンプルなページにする。公開ページは公開 repo からしか出せない。また GitHub Pages の URL は repo の名前で決まる。なので、次の順で行う。（pjdhiro 2026-11-07）
  1. 今までの repo の名前を変え（アーカイブ用の名前は、末尾に `-archive` を付ける。例：`awareness-space-archive`）、非公開にする。
  2. 同じ名前（project-design ほか）で、中身のない公開 repo を作り直す。
  3. `python3 redirects/build.py` で作った `redirects/<名前>/` の中身だけを置き、Pages で出す。今までの URL の下の階層も、新しい場所の同じ階層へ送る（404.html）。
- リンクは一度に揃えない。徐々に更新していき、そのたびに要るリンクを張り直す。（pjdhiro 2026-11-07）

## 材料の扱い

| 材料 | 扱い |
|---|---|
| 調べ方のルール（調査の手順・原典の照合・品質の検査・執筆のルール） | 最初に持ち出す。pjdhiro の指摘から生まれたものと、LLM が作ったものを分けて見直してから入れる |
| pjdhiro の発言と判断 | ページを作るときに、そのページに関わるものを集める。大切なのは生の文字列でなく趣旨。誤字・脱字は直して整える。何への答えだったかを添え、Claude の推測は混ぜない。趣旨が変わりうる直しは pjdhiro に確かめる |
| 調査結果（今までの knowledge・evidence・調査メモ・wiki） | そのままは使わない。多くは以前の LLM と作ったもので、確かめ直しが要る。要る主張だけを取り出し、一次ソースで照合し直して、通ったものを書き直す。何をどの一次ソースで確かめたかを添える |
| サイトのファイル（HTML・CSS・JS・画像） | プロジェクトデザイン論のサイトは、公開ページが読むファイルと読み物の正本・build を、そのまま複製した（2026-11-07、project-design の `develop` 7d6febb）。自分のアドレスへの参照だけを書き換えた。ほかのサイトも、順に同じように複製する |

どの材料も、入れる前に `docs/PUBLISH-CHECK.md` の点検を通す。

## ページの作り方

ページ（または機能）ごとに、次の順で進める。

1. そのページで何を言うかを決める。
2. 要る材料を今までの repo から挙げる（主張・発言・判断・図・コード）。
3. 主張は一次ソースで照合し直す。発言は趣旨を整える。迷うものは pjdhiro に確かめる。
4. 新しく書いて、手元とブラウザで確かめ、レビューを通す。
5. どの repo のどの版から何を取り、どう確かめたかを記録する。
