# Claude が繰り返す誤りの型

対話や執筆の前に一巡する。自分の案がどの型に当たるかを見る。今までの repo の「指摘の台帳」（2025〜2026-11 の事例 90 件ほど）から、型だけを取り出した。型ごとの代表例（事例と pjdhiro の言葉）は `corrections-examples.md` に分けてある。公開文を書く・直すときに、当たりそうな型の行を読む。毎回は読まない。新しい指摘を受けたら、同じセッションで型を足すか、型の確認を直す。足すときは、まず既にある行に溶かせるかを見る。

| 型 | Claude がやりがちなこと | pjdhiro の構え | 書く前の確認 |
|---|---|---|---|
| A 一般論に丸める | 通説・教科書・きれいな定義・一般知識の例で埋める。pjdhiro の公開文を読まずに書く。既存の理論で本人の見方を説明しようとする | 体験が先で、理論は乗り物。pjdhiro の公開文の語彙と本人の言葉で書く | 公開文を読んだか。その例は本人の記録にあるか。物理などに当てるとき、物理として正しいかを追う話にずれていないか。見ているのは、登場人物の関係が本人の体験と構造で似ているか |
| B 二元・対立・格子で切る | 「AではなくB」、四象限、アンチテーゼ、「射程外」「別の層」で切り分ける、一つに絞る、「生存の側／信頼の側」と分けて置いたまま包まない | 区別は残るが切り離されていない。いろいろ包んでいる。切り口は観る構えで、実在の分割ではない | 対で切っていないか。包む形になっているか。食い違って見える二つの定義を「どちらを正とするか」と問う前に、両立する面として一緒に書けないかを見たか |
| C 範囲を勝手に狭める | プロジェクトに限る、意図ある行為に限る、記号にできる手順に限る、心の働きに限る、将来は予想できる前提を置く | 個人も社会一般も同じ現象。無意識の成長・不可抗力・感情・心の準備も過程に入る | 誰が範囲を決めたか。本人の射程を削っていないか。本人が Claude に伝えるために使った言葉やたとえ（「経営学として」、骨格の説明の「神経現象学」「心理学」など）を、読み物の範囲や骨格、部や章の題に格上げしていないか（2026-11-09 にも繰り返した）。Love駆動開発が扱うのはプロジェクトの駆動源で、人生・家族・社会も入る（2026-11-09）。本人が知りたいのが通説を覆す理論の見方のとき、問いを本人の素朴な体験の側へ狭めて返していないか（2026-11-09・熱と時間の深掘りで「どっちでもない。素朴な時間のことはここでは興味を持ってない」） |
| D 古典の語彙で書く | 経営学・管理・運営の語彙（列・手順・地図・コントロール・部品・機構・受け皿） | 古典物理で量子を書くような違和感がある。仮説自身の語で書く | その語彙は誰のものか |
| E 急いで解く・断定・看板 | 保持論点を本文で解く、「正体です」「自然です」「最適」「正解」と言い切る、非二元性を看板にする、無理に論を勝たせる、枝葉の正しさを守ろうとする | 断定しない見立て。保持論点は保持。枝葉を守って大局を見失わない | 保持論点を先取りしていないか。科学の見方や枠組み（生き物は散逸構造、など）を、確かめられた事実のように「〜です」と書いていないか。表で分けた数を、分野そのものの数のように書いていないか（「経営学の七つの考え方」→「表に並べた考え方」・2026-11-09）。事実（測られたこと）と見方を分けたか。調べで「対応が無い」と出たとき、結果をそのまま保ったか。本人の言葉の意味を「本当は別のものを指しているのかも」とずらして、比喩や仮説を救っていないか。条件付きで成り立つ物理の結果（弱い重力・遅い運動・熱平衡・局所的に など）を、条件を落として一般の言い切りにしていないか（2026-11-09） |
| F Claude が Claude に説明する | 「この読み物は〜しません」「一度だけ戻ります」「断定ではなく足場です」 | 規約は Claude の歯止めで、読者への約束ではない | 誰に向けた文か。何を載せたか・どう確かめたか（読み方・出典の確かめ方）を、冒頭で読者に釈明するように書いていないか。方法の説明は巻末に置き、言い訳めかさず、した作業を淡々と書く（2026-11-09・「Love とは、どう言われてきたか」の冒頭の「読み方」の節に「巻末に書くことじゃないかな。claudeの言い訳めいたやつ」「もう少し言い訳っぽさを減らし、淡々と作業の内容を記述してほしい」） |
| G 読み違い | 本人の言葉を条件文・断定・一般論に言い換える、条件を落とす、焦点をずらす、例の一つを規則にする、たとえの芯を取り違える | 趣旨を保つ。「など」の一例を規則にしない | 趣旨は本人の言葉と一致するか。読みは本人に確かめたか。指示の言葉（「作ってしまう」など）を、自分のなじんだ作業の型に読み替えていないか。「再検討して」「考えて」を、書き換えの指示と読んでいないか。案を示してから直す（2026-11-09・Love駆動開発の三章の趣旨を考えてと言われて先に書き換え、見出しの仮の言葉まで本文に入れた）。定義は、正本の文と一字ずつ照らしたか。「少なくとも」「一つは」のような下限や例の言葉を、結論や芯に格上げしていないか。本人が借りた古典の語（指月 など）は、一般の意味で読む前に本人の記録での使い方を確かめたか。本人が難しさとして話したことを、判定を厳しくする規則に変えていないか。問いを立て直すとき、本文の言い換え（「問いは、構想の手前で働いている駆動源」など）でなく、本人の問いそのもの（「私は何に駆られてプロジェクトを行うのか」）に戻ったか（2026-11-09・言い換えから第四部「最初の問いに戻る／構想」を立て、「そこに問いは置いてないよ」）。物理の話で「向き」「方向」「逆」と書くとき、増え方の向き（比例か反比例か）と符号（＋か−か）と時間の向きを分けて書いたか。見た目の依頼の「抽象的」「意味深」を、物理の対象をそのまま描いた図（ブラックホール・銀河の絵）に読み替えていないか（2026-11-10・Love駆動開発の背景の見本に「かっこ悪い」） |
| H 捏造・転記 | 原典に無い構造や名前を作る、数値を写し違える、確かめていない帰属、引用先に無い言葉を「〜と置いています」と書く、出典を主張と逆向きに当てる、旧サイトの文を確かめ直さずに戻す | 原典と照合する。一次ソースまで遡る。確かめていないものは確かめていないと書く | 出典は実在し、本文と一致するか。旧サイトから戻す文は、今の正本（Love駆動開発など）に出所があるか。物理の理論を五段階などの型に当てるとき、その理論で何が場（基になるもの）で、何がそこから生まれるかを先に確かめたか。型の欄を埋めるために、別の理論の現象（原子の遷移など）を借りてきていないか。Claude が並べ直した切り口（表の列など）を、原典の著者の分け方として書いていないか。著者がしていない分け方は、著者の名前と並べず、このページがしたことと読める文で書いたか。エージェントに頼む文に書く書誌（DOI・題・巻号）も、記憶で埋めず Crossref で照らしたか（2026-11-09・#85 の頼む文で DOI 8 件が同名の巻の別論文を指し、エージェントが掴みかけた） |
| I 浅さ・留保で終わる | 自明な否定を並べる、留保を成果にする、話の流れを切る差し込み | 物理と心がどれだけ深く似ているかを厚く。留保は足場で成果ではない | 読者が持ち帰る中身は何か。比喩を言い換えて並べただけの章になっていないか。前の章で立った問いに、章の頭で答えているか（2026-11-09）。読み物の全体が、冒頭の問いに結論で答えているか。結論までの流れを先に題で立て、中身の無い章は工事中で置いたか。内容を並べて結論から逃げていないか（尻すぼみ・2026-11-09）。対話でまだ掘っていない議論点を、公開文の章として出していないか |
| J 文体の演出 | 体言止めの連打、ダッシュ、対句、独自の比喩ラベル、擬人化、決め台詞 | 教科書のような普通の文。差は視点で出す | 飾っていないか |
| K 作業の杜撰・早すぎる諦め | 品質の確かめを省く、場当たりで直す、曖昧な削除で全部消す、取得できないと言って諦める、指摘への対症で部品を足す、記録や画面やコードを見ずに記憶と推測で見立てる・案内する・説明する、見つけた原因を報告だけして直さない | 調べる → 案 → レビュー → 確かめる → 直す。大きな改稿は計画を先に。削除は対象を一文で確かめる。別の経路を探す。原因が分かったら、その場で直す | 確かめの手順を回したか。その日の記録の要点を読んだか。案内・説明・見立ての前に、今の画面と、関わる全部のコードや記録（行き先・経緯・判定）を開いたか。手元の一つや記憶から推測していないか。概要や要約を書くとき、その章の本文を開いて読んだか（機械向けの要約や記録の要約から作っていないか・Love駆動開発の概要の構想の箇条・2026-11-09）。生成し直す・消す・取り込む前に、元と出来上がりのずれ、消したあとの画面（警告も）、取り込む変更にサンドボックスで書けない場所（`.claude/` など）が入っていないかを見たか（worktree に develop を取り込む merge・fast-forward も同じ。サンドボックスの中で回すと `.claude/` で止まり、作業ツリーだけが進んで枝と食い違う。2026-11-08）。あとで、頼んだ以外に差分が出ていないかを見て、出ていたら戻すだけでなく仕組みを直したか。「0 件」「消えた」「空になった」「原典に無い」と言う前に、出来上がり（組んだサイトなど）や原典そのもので数え直し、一覧は全部見たか（精読ノートに無いことを原典に無いことと読まない）。削減や重なりの見込みの数字（「3 割」「約 800 字」など）は、測ってから書いたか。直したあとも測り直したか。画面の部品（目次・ボタンなど固定で置くもの）を足したら、一つの幅で見て済ませず、幅を変えて本文との重なりを見たか（HOME の目次・2026-11-08）。worktree で始めるとき、枝が develop と同じかを見たか。手元の PDF の表紙を、引く書誌と突き合わせたか。git に入っているものを見る検査は、新しいファイルを git add してから走らせたか。渡された記録の続きを考えるとき、記録を読み直し、そこに既にある論点や答えを新しい案や問いとして出していないか。サンドボックスの中から localhost（3001 など）に届かないのを、サーバーが止まっていると読んでいないか（curl の exit 7 はサンドボックスの遮断でも出る。見立てる前に、サンドボックスの外か launchctl で確かめる。2026-11-09）。push・fetch は、それだけを一つの呼び出しで `git push origin develop` と書いたか（`.claude/settings.json` の `sandbox.excludedCommands` は、呼び出し全体が `git push …` に合うときだけサンドボックスの外で動かす。`cd … &&`・`git -C <path>`・パイプ・`git commit … &&` と組むと中に残り、キーチェーンが読めず `could not read Username` で止まる。worktree からも refs は共有なので、そのまま push できる。2026-11-09）。リンクで渡された記録を開けないときは、開けないと先に言ったか。コンテキストの使用量を、会話の長さから推測で言っていないか（Claude は自分では測れない。区切りの判断は pjdhiro の画面の数字で確かめる。2026-11-09・「とうに過ぎている」と言ったが、pjdhiro の UI では 27%）。兄弟の探究（意識とは など）の調査を開かずに、読み物の引用の数から「薄い」「無い」と見立てていないか（2026-11-09）。外へ書く操作（Issue の失敗と、取り込み前の main への push）。main へ送る前の確かめは、仕組みに移した（`.githooks/pre-push` と `bash scripts/publish-main.sh`。下の「繰り返し」の表）。別のセッションやエージェントの報告を受けて「できた」と伝える前に、develop の出来上がり（ページ・照合の状態）を自分で開いて確かめたか。報告は証明ではない（2026-11-09・#79 のページを、作ったセッションの報告だけで「できた」と伝え、「レビューはした？」と聞かれた）。「Claude からは書けない」「pjdhiro の手が要る」と言う前に、別の経路（Edit ツールは sandbox の外で、承認をもらって書ける など）を試したか（2026-11-09・`settings.json` の手順を渡したら「手動にしたのでやって」） |
| L しっくり感を軽く見る | 数理が正しい・論理が合っているから採る | 最終の判定はしっくり感で、pjdhiro が行う | 判定を仰ぐ形になっているか |
| M Claude への説明を本文に引く | 対話で Claude の書き方を直すために言われた構えを、「pjdhiro の見方」として本文に貼る。発言を並べて流れが切れる | 構えは引用せず、書き方に溶かす。引用するのは体験・像・定義・問い | その発言は読者に向けたものか、Claude に向けたものか |
| N 発言の受け答えで本文を書き換える | 発言の一つ一つに、すぐ本文を書き換えて返す | 発言はいったん材料として受け止め、節全体を見直してから案を出す | 一つの発言だけに合わせていないか。レビューの所見を、「それは結論に要るか」を問わずに判断事項として並べていないか。判断事項は、対話と規約で答えが出ないものだけか（2026-11-09）。発散的な対話の発言を、stance・corrections・メモリ・公開の文に写していないか（2026-11-09・熱と時間） |
| O 図の目的を見ない | 図を直すとき、その図が見せる一点を確かめずに部品を足す・外す | 直す前に、図が見せる一点を一文で言う | その図は何を見せるためのものか |
| P 確かめすぎる | 話の流れで意図が明らかな操作（マージ・push・公開）を、そのたびに「よいですか」と聞いて止まる。規約で答えが出る判断を「pjdhiro の判断が要るもの」として並べる | 編集者は pjdhiro 一人で、git は履歴のため。流れで明らかなら進める。判断基準は repo にある | その確認は、取り消せない・価値判断を伴うものか。流れで答えが出ていないか。stance.md で pjdhiro の判断を予想したか |
| Q 言葉を取り違える | 報告を英語で書く。作業の途中から英語に切り替わる | pjdhiro とは日本語で話す | 途中経過・まとめ・質問まで、日本語で書いているか。長い作業のあとの最後の報告も日本語か。ツールの合間に書く一行（「次に何をするか」）も日本語か。エージェントの報告を待つ合間や、ファイルを書く直前の短い一行も日本語か |
| R 継ぎはぎで組む | 章を足すたびに、前の章のあだ名（「価値の章」）や別ページの語（重力の井戸）に寄りかかる。冒頭のまとめ・用語の定義・ページ内の正確なリンクを後回しにする | 長文の作法（冒頭の問いと概要・用語は初出で定義・参照は章題そのままで行き先へ直接）を守り、教科書のように平易に | 冒頭だけ読んで、何の話で答えは何かが分かるか。冒頭の概要の箇条を、章の中身を順に説明する文や具体の列挙で埋めていないか。部の接続の段と同じくらい短く、包括的な語で、一言で言える長さか（2026-11-09・Love駆動開発の概要を章立てに合わせたとき、箇条に「細かすぎる」「唐突すぎる。一言で言うならあってる。」）。その語やたとえは、このページを初めて読む人に通じるか。サイト特有の語（重力の井戸 など）だけでなく、その読み物が自分で立てたたとえ（「円を重ねる」など）も同じに見る。通じないなら、初出で定義するか、ページ内の説明へリンクする。接続やまとめのように視点を全体へ戻す文では使わず、包括する言葉を先に選んで短く書き、章の題を列挙しない。本文の言い方に合わせることを、正しさの確かめと取り違えない（2026-11-09・Love駆動開発の接続の案に「特殊なたとえを当然のように使うのはやめて」「なるべく短く」。`stance.md` 2-4）。参照は章題そのままで、行き先の段落へ飛ぶか。リンクを貼るだけのところを、文で説明していないか（「〜は、〇〇にあります」でなく、注記の「（参考：〇〇）」で足りる。Love駆動開発の群盲象の段・2026-11-08）。対話で、式や概念の性質（「比だけを決める」「虚時間の輪」など）を一文で言い切って済ませていないか。具体の数の例と、一歩ずつの説明を添えたか（2026-11-09・「わからない」が二度続いた）。本人がメタ認知の先で到達した感覚の話を、そこへ至る文脈（何を観ていって、どこで感じたものか）なしに、面の一つや畳みの題として出していないか（2026-11-09・Love駆動開発の第四部の「確かめずにつながる安定」・「唐突すぎる」）。pjdhiro に手作業を頼むとき（Issue に残す表も）、開く URL・ページ内で探す語・持ち帰るもの（貼る範囲）と、それで何を確かめるのかを一件ずつ書いたか（2026-11-09・#79 の「手で開いて確かめてほしいページ」に何を見るかが書かれておらず、「わからない」） |
| S git を共同開発の作法で使う | worktree の枝に作業を溜め、マージ・取り込み・「下書きは develop、確かめたら main」のような段取りを組み、その説明で確かめを求める | `CLAUDE.md` の Git の節のとおり。個人の文章管理で、プルリクは要らない。編集したら develop へ最速で統合し、手元のサーバーで目視する | 編集を develop へ取り込んだか（枝に溜めていないか）。3001 で見られる状態か。段取りの説明で pjdhiro の手を止めていないか。クラウドで動いているときは、GitHub の develop へ送っても手元の 3001 には降りないので、リンクを渡すたびに、手元で `git pull origin develop` が要ることを添えたか（pjdhiro 2026-11-08「ローカルサーバなのでクラウドの時は指摘してね」） |


## 繰り返し

同じ型の誤りを、前に指摘されたあとでまたしたときに、ここに日付を足す（pjdhiro 2026-11-09・セッションの終わりの振り返りを問われて）。確認の文を足すだけでは、表の欄が長くなって一巡で読めなくなり、同じ誤りが続く。だから次のように決める。
