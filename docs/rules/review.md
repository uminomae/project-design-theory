# 読み物の念入りなレビュー（pd）

pd の読み物（`pd/reader/*.html`。正本は `pd/knowledge/research/*/READER-*.md`）を、develop に入れたあと・main に出す前に、念入りに見る手順。創造とは（cs）の全体レビューの決まり（`docs/cs-review/README.md`「レビューの決まり」「エージェントの分け方」「機械の点検」）を手本に、pd の読み物に合わせた。初版は 2026-11-09、#79 のページ「Love とは、どう言われてきたか」のレビューで書き、回して分かったことで直した（pjdhiro 2026-11-09「#79 のレビューはした？しっかりとしたレビューをするルールやスキルはある？」→「始める」）。

別のセッションの「作った・照合した」という報告は証明ではない（型 K）。レビューは、その報告を出来上がりで確かめ直す作業。

## 1. 決まり

- 指摘ごとに、場所（正本の行か見出し）・何が問題か・根拠・照合の状態（`sources.md` §3）・重さを書く。
- 重さは三つ。高＝誤り・捏造・帰属違い・数字や書誌の食い違い・原典に無い構造・**本文照合済でない出典が本文に載っていること**。中＝言い過ぎ・こじつけ・定義のずれ・確かめた度合いより強い書き方・善悪の判断の混入。低＝文体・表示。
- 公開文に載せるのは、原典の本文を読んで確かめたものだけ（`sources.md` §3-3・stance 2-6。pjdhiro 2026-11-09・#79）。書誌だけ・要旨だけ・二次資料だけ・記憶だけの項目、取れなかった文献の一覧、「まだ読めていない」の断り書きは、読み物に置かない。見つけたら重さ 高 とし、直し方の案は二択で並べる：本文を読める取得先（可と不可の線は `sources.md` §5 の決まり 8。個人が上げた権利未確認の写しだけは不可）を探して本文照合済に上げる／読めなければ本文から外し、照合の状態ごと Issue に残す。
- 推測と確かめたことを分けて書く。原典の本文で読んだものだけを「本文照合済」と書き、位置（頁・節・偈の番号）を添える。
- 見つけてもすぐ本文を書き換えない。一巡してからまとめて案を出す（型 N）。機械的な誤り（DOI・書誌・切れたリンク・綴り・数の食い違い）だけは、記録してから判断を待たずに直してよい（stance 2-5）。直すときは、正本 → 生成 → check.sh → commit → develop の順に通す。
- テンプレートやスクリプトが原因のものは、個別に直さず、原因を直す（型 K）。
- pjdhiro の判断が要るもの（理論との距離・善悪・東洋の像の読み・採否）は、`stance.md`・`stance-theories.md` で答えを予想してから残す（型 P）。答えが出るものは決めて進める。
- 報告・途中経過・エージェントへの頼みは日本語（型 Q）。
- pjdhiro に見せるときは md でなくページ（アーティファクト）。Issue にはページの URL と要点をコメントする。

## 3. エージェントの分け方

司令塔は Fable（その時の最新）、エージェントは Opus（② 内容の照合は `effort: "high"`、③・⑤ は `"medium"`）をバックグラウンドで（`docs/cs-review/README.md`「エージェントの分け方」）。モデルや effort を替えるときは、`docs/cs-review/README.md`「エージェントの分け方」の比べ方を通す。広く探す役は Explore でなく `model: "haiku"` のエージェントに（同じ節・2026-11-10）。司令塔は材料を自分で読み込まず、割り振り・要の点の確かめ直し・規約で答えが出る判断・一覧の仕上げ・develop への取り込みをする。

- ② は分野ごとに分ける（#79 では、仏教と儒教・新約とアウグスティヌス／ギリシャから二十世紀の哲学／近代以降と心理学・神経科学・分裂の分け方、の三人）。
- ③ は一人。② と重なる指摘は、司令塔が一覧で一つにまとめる。
- ⑤ は一人。渡すのは抜いた文字のファイルだけ。正本・規約・会話を渡すと、文脈ゼロにならない。
- ①・④ は司令塔。画面はブラウザが一つなので同時に一つ。

頼む文に必ず入れること：日本語で作業・報告する／書いてよい場所（報告のファイル一つ。repo には書かない。commit・push しない）／材料の在りか（正本・生成物・一覧の表・Issue）／先に読む規約（`sources.md`・`writing.md`・`corrections.md`・`stance.md` §1・§2-6・§4・`stance-theories.md`）／指摘の形（§1）／原典の取り方（公開の原典サイトは読んでよい。自動取得を拒むサイトは繰り返さず、「ブラウザでの保存が要る」と書く。個人の写しは性格を添える）。

エージェントの指摘は、要の点を司令塔が確かめ直してから一覧に載せる（うのみにしない）。

## 4. 一覧と報告の形

- 一覧：場所・問題・根拠・照合の状態・重さ・直し方の案（高・中）・判断が要るか（要るなら stance で予想した答え）。重さ 高 を先に。
- ページ（アーティファクト）にして pjdhiro に見せ、Issue にページの URL と要点をコメントする。
- 機械的な誤りは、記録してから直し、生成・check.sh・commit・develop・3001 で目視まで通す。
- セッションの記録（`.cache/session/`）に、回した点検・指摘の数・直したもの・残したものを書く。pjdhiro の判断があれば `stance.md`・`decisions.md`、Claude の誤りの指摘があれば `corrections.md` に足す。

## 5. 回して分かったこと

- 2026-11-09（#79「Love とは、どう言われてきたか」。5 人・約 70 分・エージェント 5 人で 83 万トークン）：
  - 引用の捏造や位置の誤りは、抜き取り 44 項目で一つも無かった。重かったのは、規約の側（載せてよい照合の状態）・帰属・章題の看板・作業メモの混入・冒頭の用語。内容の照合だけでなく、③ と ⑤ を必ず回す。
  - ③ 文体と ⑤ 読解が、独立に同じ箇所（冒頭の用語・「統合の反対側」・照合の状態と凡例の食い違い）を指した。二人が重なった指摘は、司令塔が確かめ直す前から重さを上げてよい。
  - レビューの途中で正本が develop 側で更新された（道元・Legge 訳）。エージェントを起こす前に `git merge develop` をサンドボックスの外で済ませ、頼む文に commit の番号を書く。行番号で頼むと、ずれる。見出しと鍵の文で頼む。
  - 正本の行番号は、エージェントの報告の時点のもの。司令塔は行番号でなく内容（grep）で確かめ直す。
  - 文字層の無い PDF（Stony Brook の Bowlby 1958）は pdftotext で読めない。エージェントが「地の文に〜がある」と言うものは、司令塔が別の手段（OCR か目視）で確かめるまで「司令塔は未確認」と書く。
  - ① の外部リンクの生死は、ホストを全部 `allowed_domains` に書いて一度で回す。DOI の転送先（doi.apa.org・idp.nature.com など）も要る。出版社の 403 は生きている扱い。
  - ⑤ の抽出スクリプトに spec の無いページ用の共通の七問を足した。ページごとの質問（#62）は別。
  - 機械的な誤りで司令塔が確かめ直せなかったもの（Diels の頁）は直さず、一覧に「司令塔は未確認」として残す。
  - pjdhiro に見せる一覧は、重さで絞れるページにした。Issue のコメントは要点と URL だけ。
