# 型 K の確認（作業の種類ごと）

`corrections.md` の型 K（作業の杜撰・早すぎる諦め）の「書く前の確認」を、作業の種類で分けて置く。毎回は読まない。その作業を始める前に、当たる節だけを読む。K0 はどの作業でも読む。

経緯：確認の文が 30 項目を超え、一巡では読めなくなった。「繰り返し」の決まりに従い、次に型 K を繰り返したら分けることにしていた。2026-11-10 に繰り返したので、表の一つの欄から、この文書の節に分けた（stance 2-8「規約と記録は、毎回読む分を小さく保つ」）。中身は削らず、重なるものは一つに溶かした。型 K の繰り返しの記録も、この文書の終わりに移した。

| 節 | いつ読む |
|---|---|
| K0 どの作業でも | 見立て・案内・説明をする前。「できた」「書けない」と言う前 |
| K1 git とサンドボックス | worktree で始める・develop を取り込む・push する・外へ書く前。**規約を読む前に、取り込みを回さない** |
| K2 生成・検査と数え直し | 生成し直す・消す・検査を走らせる前。数や「無い」を言う前 |
| K3 画面 | 画面の部品を足す・考える前と、足したあと。3001 で確かめるとき |
| K4 調べと記録 | 記録・原典・兄弟の探究から、見立て・要約・続きを書く前 |

## K0 どの作業でも

- 確かめの手順（調べる → 案 → レビュー → 確かめる → 直す）を回したか。
- 案内・説明・見立ての前に、今の画面と、関わる全部のコードや記録（行き先・経緯・判定）と、関わる規約の行（計画の「規約で決めたこと」など）を開いたか。手元の一つや記憶から推測していないか（規約の行は 2026-11-10・as のレビューの A01 で、計画に決めてあったことを開かずに「直すところ」とした）。
- 別のセッションやエージェントの報告や成果物を pjdhiro に伝える前に、指された実物（develop の出来上がり・照合の状態・挙げられたファイルの中身）を自分で開き、頼んだ問いに中身が答えているかを読んだか。出所が付いているか・形がそろっているかを見ただけで「確かめた」と言っていないか（2026-11-10・下の「繰り返し」の最後の行）。「できた」も「誤り」「公開してはいけない」も同じ。報告は証明ではなく、重さは名前や決まりの文からでなく中身から付ける（2026-11-09・#79 のページを、作ったセッションの報告だけで「できた」と伝え、「レビューはした？」と聞かれた。2026-11-10・下の「繰り返し」の最後の行）。
- 「Claude からは書けない」「pjdhiro の手が要る」と言う前に、別の経路（Edit ツールは sandbox の外で、承認をもらって書ける など）を試したか（2026-11-09・`settings.json` の手順を渡したら「手動にしたのでやって」）。
- エージェントに頼む文で指したファイル（頼む文の雛形・レビューの全文・鍵の文の控え）は、頼む呼び出しより前に書き終えたか。同じ応答で、頼む呼び出しを先に並べていないか（2026-11-10・as の論点と回答で、レビューの全文のファイルを頼んだあとに書き、エージェントが読めずに一周を余分に回した）。
- コンテキストの使用量を、会話の長さから推測で言っていないか（Claude は自分では測れない。区切りの判断は pjdhiro の画面の数字で確かめる。2026-11-09・「とうに過ぎている」と言ったが、pjdhiro の UI では 27%）。

## K1 git とサンドボックス

- worktree の始めに develop へ揃えるのは、仕組みに移した（`bash scripts/sync-develop.sh`）。枝が develop より古く、枝に `scripts/sync-develop.sh` が無いときは、`git merge --ff-only develop` だけを一つの呼び出しで回す（`sandbox.excludedCommands` に入っているので外で動く）。`--ff-only` を外した `git merge`・`git pull` をサンドボックスの中で回すのは、仕組みで止める（`.claude/hooks/guard-git-merge.sh`。2026-11-10・11-11）。`sync-develop.sh` が止まったら、その案内に従う。
- 取り込み（merge・pull）をほかのコマンドと組む呼び出しは、仕組みに移した（2026-11-10）：`.claude/hooks/guard-git-merge.sh` が止める。`.claude/settings.json` の `sandbox.excludedCommands` は、`bash scripts/sync-develop.sh`・`git merge --ff-only *`・`git -C * merge --ff-only *` を、呼び出しの全体が合うときだけサンドボックスの外で動かす。
- main へ送る前の確かめは、仕組みに移した（`.githooks/pre-push` と `bash scripts/publish-main.sh`）。自分の commit だけを main へ送る枝は、`bash scripts/pick-to-main.sh <枝> <commit>…` で作る（作業ツリーに触らない。worktree で `git switch` しない。2026-11-10）。
- push は、それだけを一つの呼び出しで `git push origin develop` と書いたか（`cd … &&`・パイプ・リダイレクトと組むとサンドボックスの中に残り、`could not read Username` で止まる。worktree からも refs は共有なので、そのまま push できる。2026-11-09）。
- worktree の枝を本体の develop へ取り込むとき、取り込む変更に `.claude/` が入っていれば、サンドボックスの外で回したか（中で回すと `.claude/` で止まり、作業ツリーだけが進んで枝と食い違う。2026-11-08・11-10）。
- 検査の結果を `| tail` に通すと、終了コードが tail のものになり、失敗が隠れて次の段（commit・main への push）が進む。終了コードを見るものは、ログに落として `$?` を見たか（2026-11-09・check.sh の失敗）。ログの名前には、セッションの名前を入れたか（サンドボックスの `$TMPDIR` はセッションのあいだで共有。2026-11-10・`pm.log` という名前で落とし、別のセッションの同じ名前のログの終わりを自分の結果として読みかけた）。
- 外へ書く操作（Issue の本文の上書きなど）の前に、送る中身が空でないかを確かめ、前の段が失敗したら止まる形（`&&`）でつないだか。
- サンドボックスの中から localhost（3001 など）に届かないのを、サーバーが止まっていると読んでいないか（curl の exit 7 はサンドボックスの遮断でも出る。見立てる前に、サンドボックスの外か launchctl で確かめる。2026-11-09）。

## K2 生成・検査と数え直し

- 生成し直す・消す・取り込む前に、元と出来上がりのずれと、消したあとの画面（警告も）を見たか。あとで、頼んだ以外に差分が出ていないかを見て、出ていたら戻すだけでなく仕組みを直したか（代表例は `corrections-examples.md` の K・2026-11-08 の最終更新の日付）。
- 「0 件」「消えた」「空になった」「原典に無い」と言う前に、出来上がり（組んだサイトなど）や原典そのもので数え直し、一覧は全部見たか（精読ノートに無いことを原典に無いことと読まない）。
- 削減や重なりの見込みの数字（「3 割」「約 800 字」など）は、測ってから書いたか。直したあとも測り直したか。
- git に入っているものを見る検査は、新しいファイルを git add してから走らせたか。

## K3 画面

- 画面の部品（目次・ボタンなど固定で置くもの）を足したら、一つの幅で見て済ませず、幅を変えて本文との重なりを見たか（HOME の目次・2026-11-08）。
- 画面の部品（下へ促す印など）を新しく考える前に、手本（cs・ks）に同じ役の部品があるかを開いて見たか（2026-11-10・Love駆動開発の最初の画面で、細い線の印を新しく作り「cs/?graphic=i を参考にして」）。
- 背景や部品の JS を直したら、commit の前に、直した worktree のサーバー（3010 ほか）でページを読み込み、その部品が動いているか（コンソールの警告・`window.loveMembrane` などの入口があるか）を見たか。構文の検査（`node --check`）は、同じ名前の二重の宣言のような読み込みのときの誤りを通す（2026-11-10・Love駆動開発の膜で、WebGL を作り直す直しに元の `const renderer` を残したまま commit し、膜が読み込めず別の背景に落ちていた。develop に入れる前の確かめで見つけた）。
- 3001 に届かないときは、K1 の localhost の行を見る。

## K4 調べと記録

- その日の記録の要点を読んだか（`bash scripts/session-digest.sh`）。
- 概要や要約を書くとき、その章の本文を開いて読んだか（機械向けの要約や記録の要約から作っていないか・Love駆動開発の概要の構想の箇条・2026-11-09）。
- 渡された記録の続きを考えるとき、記録を読み直し、そこに既にある論点や答えを新しい案や問いとして出していないか。
- リンクで渡された記録を開けないときは、開けないと先に言ったか。
- 兄弟の探究（意識とは など）の調査を開かずに、読み物の引用の数から「薄い」「無い」と見立てていないか（2026-11-09）。
- 手元の PDF の表紙を、引く書誌と突き合わせたか。
