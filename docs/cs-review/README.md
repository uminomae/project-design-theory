## なぜするか

cs は、30 の学術領域に、創造の5段階モデル（場・波・縁・渦・束）と似た構造があるかを調べた成果。調査の手法（領域ごとに理論を集め、原典で照合し、5段階との対応を見る）は間違っていない。ただし作ったのは当時の LLM（Opus 4）で、誤り・誤解・中途半端に終えた箇所・wiki との食い違い・未熟な UI が、あらゆるところに残っている（pjdhiro 2026-11-08）。

このレビューの目的は、cs を、今の規約（`docs/rules/`）と正本（Love駆動開発・ks・as）にそろった部品のサイトに組み直す材料をそろえること。直すのは、材料と判断がそろってから。

### 中心の問い

論の全体が cs に頼っているのは、ほぼ一点。

- Love駆動開発の正本は、cs を「渦がどれだけありふれているかを、30 の学問領域で示す」ものとして引く（`READER-love-driven-dev.md` 877 行・1016 行）。
- stance 2-1：「創造は 30 の分野で同じ形が報告されているほど普遍的と見ているが、信頼はまだそこまでではない。固さの違いは書き分ける」。

30 の分野の調査は、分野ごとに合否を付けて数えるためのものではない。一面を集めて並べるためのもの（pjdhiro 2026-11-08）：

> 例えば出発点を正反合としましょう。それに似ているものを探すと、電子の誕生も似ているとなる。では、どんな対立、衝突、統合だったか、を並べていくと、5段階の構造とプロセスを、群盲象を評すようにわかってくると思うのです。どれも一面でどれも間違えてはいない。

なので、このレビューの中心の問いは「**30 の分野で、何と何が対立し、どう衝突し、どう統合され、何が新たな安定になったか。それを原典で確かめて並べる**」。並べた一面から、五段階の構造とプロセスが見えてくる。誤りの一覧（帰属・数・書誌）は、一面を正しく写すための点検。

- 領域ごとの記録の芯は、一面の表：その分野の論ごとに、対立（何と何が）・衝突（どうぶつかったか）・統合（どう包まれたか）・新たな安定（何が残ったか）を一行に書き、原典で確かめた度合いを添える。統合に至らなかった例も行として並べ、「どう終わったか」（片方の勝利で波に留まる・場に戻る、分裂・消散・固着・凍結・暴走など）を書く。外には置かない。
- 「固さ」（stance 2-1）は、並べた一面のうち、どれだけが原典で確かめられたかとして添える。分野に合否を付けない。
- **統合に至らない型と、その境目も並べる**（pjdhiro 2026-11-08「衝突や対立が統合に失敗するパターンもあるはずです。それも分類できると良いのです。成功と失敗の境界線」）。段 3 で、至らずに終わる型を分類し、統合に至る型との境目（閾値・条件）を見る。材料：テーマ T2「閾値」の 4 分類と「渦に至らない道」（分裂・固着・ブロック・超臨界流体）、T7+T9 の失敗モード（凍結・消散・固着・暴走・ロックイン）、D10 の失敗モード 4 型、D14 の不協和の低減（意見の変化と、ほかの認知の重さを変えることを含む。報告の「合理化（波の消去）」は原典に無い分け方で、2026-11-10 に言い換えた）、D05 の「不発の記録」、分かれ道（D25 社会劇の再統合か分裂、D10 移植の拒絶か寛容、D04 内共生の共生か消化）、D02・D03 の臨界核、#50「創造を生む対立と、そうでない対立は何が違うのか」。どれもそのまま採らず、並べ直す。「悪い束」（ロックイン・鉄の檻。統合はしたが固まって動かない）も統合として扱う（pjdhiro 2026-11-08「悪い統合も統合としてください。善悪判断は人や社会の倫理観や文化で変わる」）。成功と失敗の境目は、統合に至ったかどうかだけで見て、統合の良し悪しでは分けない。統合せずに片方が勝つ形は、統合ではなく、波として揺らいでいる、または場に戻って新たな対立を待つ状態として並べる（pjdhiro 2026-11-08）。報告の分かれ道では、D10 移植の「拒絶」がこれに当たる。ただし D10 の記録では、移植の論は本文を読めなかった論に入る（要旨で確かめたのは Kawai ら 2008 だけで、同じ処置の 5 人のうち 1 人に拒絶が起き、4 人は免疫抑制薬をやめても腎機能が安定した。Medawar 1944・1953 は未照合。2026-11-10 の J11 の直しで分けた）。D04 内共生の「消化」は、2026-11-09 の照合で Sagan 1967 の本文に無く、報告と退避版の付け足しと分かったので、例から外す。並べ方は三つ：統合（良い統合も悪い統合も）／片方の勝利（波に留まる・場に戻る）／そのほかの至らない形（分裂・消散・凍結・暴走など）。「失敗」は統合に至らないことの名前で、善悪の判断ではない（stance 1-2）。
- **似ているかどうかの芯は、対立や衝突が欠かせないこと**（pjdhiro 2026-11-08「ポイントは対立や衝突が必須であることです」）。安定に変化が起き、衝突し、統合されて新たな安定になる。対立や衝突を通らずに新しいものが生まれる、と書く論は、似ているとは言いにくい。衝突の相手は良いこと以外のもの：「嫌なことや悪いことなど、良いこと以外と衝突するように包摂して進むということです」（pjdhiro）。領域の照合では、原典で二つを確かめる。その論は、嫌なこと・悪いこと・望まないことを過程の外に置かず、中に含めているか。それとぶつかることが、新しいものが生まれるのに欠かせない形になっているか。良いものだけで調和して進むように描く論や、報告が理論の理想の像だけを取り出して当てはめている所（stance-theories.md の内発的動機・心理的安全性と同じ形）は、似ているとは言いにくい（#50「どんな対立が創造を生むのか」とつながる）。「包摂」は、schema と wiki で渦のプロセスに置かれている語（「包摂・融合」）と同じで、つながりは定義の文を書くときに pjdhiro に見せる。
- 論ごとに、見ている単位の大きさ（微細さ）が違う（stance 2-1）。量子論は海の一粒まで見ようとし、生殖の論は母体・オスメス・出産・子孫のような大きな単位で見ている。五段階は pjdhiro の体験の細かさで書かれている。粗い論も、上の芯があれば似ていると数えてよい。「正反合と言った程度でも似てると思います」（pjdhiro）。粗い論で段階の一部が見えないのは、いくつかの段階が一つの語にまとまっているからかもしれず、反証とは限らない。微細さは、対応の見え方の違いを説明するために一言添えるだけにし、割り引きには使わない。評価でなく、見ている単位の大きさとして書く。
- 段 3 で、30 領域の一面を並べ、対立・衝突・統合のしかたの違いを見る。今の 5 テーマのうち「縁の類型」「閾値」は、すでにこの並べ方に近い。「28/30」のような数は主役から外す。見えてきたことは「〜かもしれない」の見立てで書き、しっくり感と固さの判定は pjdhiro が行う（stance 2-1・型 L）。
- 照合し直して弱まる領域があっても、そのまま書く。「直接示した研究には当たらなかった」と書けることも成果（`sources.md` §1-5）。
- 結果は、stance 2-1 の「固さ」と、Love駆動開発の正本の 877 行・1016 行の言い方に返す。

### 調査の手順（一つの分野）

pjdhiro 2026-11-08：「一次情報を読みながら既存の論をチェックし、修正したり、追加したり。これで 10 個ほどの論を分野ごとに。記録は md で。それを UI で見られるようにしていく。公開ページのコンテンツのスタイルは既存のもので構いません」。

1. 分野ごとに、論を 10 ほど。**すでに集めた原典をベースにする**（pjdhiro 2026-11-08「すでに収集した論文をベースにしてね。不足してる分野はさらに探してね」）。ベースは、原典の台帳 `cs/knowledge/raw/manifest.md` の行、手元の PDF（`cs/knowledge/raw/`）、精読ノート（`cs/knowledge/source-notes/`・`pd/wiki/sources/`）。今の報告が取り上げた論のうち、集めた原典が無いものは、まず探し、見つからなければ照合の状態を書いて残すか、集めた原典のある論に差し替える。読める原典で 10 に届かない分野は、さらに探す（下の表）。報告に無い論をどこまで足すかの目安（2026-11-08・D20 で足りなかった）：まず報告の論を一次情報で確かめることが先で、足すのは、手元の PDF か OA で本文に当たれて、その分野の衝突や至らない形をはっきり書いている論（Folke の適応的ガバナンス、Engel の生物心理社会モデルのように）。本文に当たれない論は足さない。報告の論が書籍だけで半分以上が未照合になる分野でも、論の数を増やすために似た論文を並べない。見つけた原典は、司令塔が台帳に行を足し（台帳は公開）、PDF は手元の `cs/knowledge/raw/` に置く（git の外）。
2. 論ごとに、URL があるかダウンロードできる一次情報（pjdhiro と第三者が確かめられるもの）を探して読む。確かめ先（URL・DOI・manifest の行）と読んだ頁を残す（`sources.md` §2-5）。
3. 今の報告の記述を、その一次情報で確かめ、直す。一次情報が見つからない論は、照合の状態を正直に書いて残すか、確かめられる論に差し替える。足りない論は足す（たとえば、正反合の系譜は 30 領域のどこにも無い）。
4. 論ごとに、何と何が対立し、どう衝突し、どう統合され、何が新たな安定になったか（または統合に至らずにどう終わったか）を一行に書く（中心の問い）。
5. 記録は、分野ごとに一つの md にする（下の「記録の形」）。
6. 一つの分野が済むごとに、その md を cs の UI で見られるようにする。見た目は今の公開ページのものでよい。仕組みは 2026-11-08 に作った：`cs/evidence/reviewed.json` に分野の行（id・file・reviewed）を足すと、トップの「30領域調査報告」のマスと分野のモーダルが、pjdhiro の repo の報告より先にその md を読む（日本語の画面だけ。英語は今までの報告のまま）。マスに「一次情報で照合済」の印、モーダルに照合日が出る。記録には PDF が無いので PDF のボタンは出ない。「30領域調査報告」のマスの中身は、開いたマスごとに一度だけ読まれてそのまま残るので、取り込んだあとは再読み込みしないと新しい記録に変わらない（2026-11-08 に pjdhiro が D14 で見た）。確かめは `?domain=Dxx` で開くか、再読み込みしてから。

## 何を正とするか

食い違いを見つけたとき、上を正とする。

1. 規約：`docs/rules/stance.md`・`corrections.md`・`writing.md`・`sources.md`。
2. 正本の読み物：Love駆動開発（`pd/`）・欠損駆動思考（`ks/`）・意識とは（`as/`）。隣の概念（欠損・抱持・欠損駆動思考・Love駆動開発）の定義はここから写す。
3. 原典の本文（PDF）。ページを控えて照合したもの。
4. wiki の精読ノート。原典で照合し直したものだけ。
5. cs の `knowledge/`（five-stages-guide・glossary・schema）。
6. 報告の本文・evidence の archive・DR（GPT の Deep Research）。探す手がかりとしてだけ使う。DR は原文が保存されておらず、出典が記号のまま辿れない。

5段階の定義は、今は六か所ほどに分かれている。食い違って見える定義は、どれかを選ぶ前に、両立する面として一緒に書けないかを見る（束は両立、pjdhiro 2026-11-08）。書き方は pjdhiro が決める（下の「判断が要ること」）。決まるまで、領域の当てはめの判定は保留にする。

### 2. 領域ごとの照合（30 領域）

一つの領域を一つのセッション（またはエージェント）で回す。二周に分ける。

1. 照合の周：報告の主張を一行ずつ取り出し、根拠の文献・wiki・PDF の有無を表にする。PDF がある文献は本文の該当箇所を読み、ページを控える。書誌は DOI を Crossref で引いて確かめる。
2. 当てはめと文体の周：5段階への当てはめがこじつけでないか（反例・語が同じだけの対応・藁人形の議論）、文章が `writing.md` と `corrections.md` に沿っているかを見る。

順：原典の PDF がある領域から。2026-04 の再監査の計画（`cs/evidence/investigation/original-access-rerun-plan.md` 41〜48 行）の群分けも使う。第 1 群（原典が取りやすく、公開報告への影響も大きい）は D08・D10・D14・D18・D20・D21・D22・D25。第 3 群（書籍に頼る）は D13・D15・D19・D24・D30。数学・物理・複雑系は物理の主張の三区別（`sources.md` §6）が要るので、同じ手で続けて回す。

判定の語は、`sources.md` §3 の四つ（本文照合済・要旨照合済・二次資料のみ・未照合）と、この計画の判定（一致・言い過ぎ・取り違え・帰属違い・付け足し・抜け・未判定）だけを使う。「抜け」は、原典にある衝突や至らない形を報告が落としていること（D18 で足した。2026-11-08）。版の間で対応段階や件数が違うものは「未判定（版の食い違い）」と書く。旧い語（verified・accepted・plausible・overstated・direct・sim・archive-historical）は使わない。照合できなかった主張を本文から「除外」しない（旧 `reader-rules-creation.md` §8F と逆。`sources.md` §3-3）。

## レビューの決まり

- 指摘ごとに、場所（ファイルと行または見出し）・何が問題か・根拠・照合の状態（`sources.md` §3）・重さを書く。
- 重さは三つ。高＝誤り・捏造・帰属違い・数字の食い違い。中＝言い過ぎ・こじつけ・定義のずれ。低＝文体・表示。
- 推測と確かめたことを分けて書く。原典の本文で読んだものだけを「本文照合済」と書き、ページを添える。
- 見つけてもすぐ本文を書き換えない。領域を一巡してから、まとめて案を出す（型 N）。ただし、機械的な誤り（DOI・書誌・切れたリンク・人名の綴り）は、その領域の記録が済んだら判断を待たずに直す（stance 2-5「整合の取れていない状態を放置しない」、2-7「公開 PDF の切れたリンクは次の改訂を待たずに作り直す」）。直すときは、出どころから生成物まで通す（段 6）。
- テンプレートや規則が原因のものは、個別に直さず、原因のほうを直す（型 K）。
- 物理と数学の主張には、教科書・研究の一線・Claude の読み替え のどれかを添える（`sources.md` §6）。数学の記述の正しさは Claude が引き受ける。
- 当てはめを確かめるときは、合うところを増やすより、その対応が禁じるもの（反例）を探す（`sources.md` §6）。
- pjdhiro の判断が要るものは、`stance.md` で答えを予想してから残す（型 P）。答えが出るものは決めて進める。
- 報告や対話は日本語で書く（型 Q）。エージェントへの頼みにも、日本語で報告するよう書く。
- pjdhiro に確かめを頼むときは、md でなくページ（アーティファクト）にして見せる。

### エージェントの分け方

**Fable が司令塔になり、Opus をバックで走らせながら組み上げる**（pjdhiro 2026-11-08「fable が司令塔となり、opus をバックで走らせながら構築していくのが良いと思っています」）。

- 司令塔（親のセッション、Fable。版は番号で固定せず、その時の最新を使う。2026-11-10 は 5.2）：計画と割り振り、エージェントの報告の要の点の確かめ直し、規約で答えが出る判断、記録の仕上げ、develop への取り込み、UI の組み立て。材料は自分で読み込まず、エージェントの報告を受け取る。
- エージェント（Opus、`model: "opus"`・`effort: "medium"`、バックグラウンド）：下の表の役。司令塔はエージェントが走っている間に、別の分野の割り振りや、済んだ分野の仕上げを進める。

考える量（effort）と、モデルや effort を替えるときの決め（2026-11-10・公式の記事「Which Claude model should you build with?」と、ドキュメント「Choosing the right model」を読んで）：

- 内容の照合のエージェントは `effort: "high"` と書いて頼む。ほかの役（定義と wiki・画面・画面のコード）は `effort: "medium"`（Opus の既定と同じ）。30 分野は指定せずに回した。司令塔は Claude Code の既定（Fable は medium）のまま。xhigh・max は使わない。記事は、モデルを替えるより effort を替えるほうが効くことが多い、と書く。
- 照合を high にしたのは、下の比べ方を農学・生態学で一度回した結果（2026-11-10）。前回の記録を読ませずに、同じ頼む文で medium と high を同時に回した：

  | | 前回（11-09・指定なし） | medium | high |
  |---|---|---|---|
  | 時間・トークン | 25 分ほど・34 万ほど | 23 分・30 万 | 31 分・45 万 |
  | 論（本文照合済／未照合） | 11（10／1） | 11（9／2） | 10（10／0。3 つは同じ著者の論文や後の総説で） |
  | 報告への所見（うち高） | — | 24（3） | 37（6） |
  | 新しく取れた原典 | — | 無し | With & Crist 1995（研究室の写しが Wayback に）・Bestelmeyer ら 2017（OA の章）ほか |
  | 精読ノート・台帳の誤り | — | DOI 2・台帳の状態 1 | DOI 1・Pedigo の頁 4 行・台帳の状態 1 |

  司令塔の確かめ直しでは、どちらにも食い違いは無かった（medium の DOI 二つ・手元の PDF と台帳、high の Pedigo の頁・With & Crist の写し）。high は 1.5 倍のトークンで、medium も前回も落とした至らない形（殺虫剤が招く再発と抵抗性・窒素の流出）を高として挙げ、取れないとされていた原典を取った。一つの分野・一回ずつの比べなので、回すごとの揺れは分かっていない。前回の結果は台帳と精読ノートに入っていて、前回の列とは同じ条件で比べられない。
- 替える前に、済んだ分野を一つ、替える前と後の形で、別々のセッションに回し直し、前回の記録と比べる。比べるのは、照合の状態ごとの数、司令塔の確かめ直しで見つかった食い違い、時間とトークン（上の表の列）。替えるのは、食い違いが減るか、同じ質で時間かトークンが減るときだけ。
- 司令塔が repo や記録を広く探すときは、Explore でなく `model: "haiku"` のエージェントに頼む。Explore はセッションと同じモデル（Fable）で走り、Fable の値段がかかる。Haiku に回すのは、見つけた場所を報告させるところまで。読んで判断するのは司令塔か Opus のエージェント（pjdhiro 2026-11-10「探す役に使ってよい」）。
- 足りないときに上げる順は、確かめの道具（`check-cs-evidence.mjs` の点検など）を足す → effort を一段上げる → モデルを上げる（上げたモデルは effort を一段下げて始める）。

試しの一巡では、内容の照合と、定義と wiki を、エージェントに分けた。画面は親のセッションが見た。本番では次の四つに分ける。頼む文の雛形は `prompts.md`。

| 役 | 見るもの | 頼み方 |
|---|---|---|
| 内容の照合 | 一つの分野の今の報告・evidence（退避版を含む）・wiki・一次情報 | `cs/evidence/evidence-Dxx-*.md` の下書きを書く（「記録の形」）。判断が要るものを報告する |
| 定義と wiki | 5段階と隣の概念の定義の置き場、wiki の frontmatter と対応 | 読むだけ。置き場ごとの対照表と、正とする候補 |
| 画面 | 3001 の cs（PC とスマートフォン幅） | 読むだけ。スクリーンショットと、文言・操作・読みやすさの指摘。ブラウザは一つなので、同時に一つだけ走らせる |

### 機械の点検

試しの一巡で、手作業で見つけたもののうち、機械でできるもの。

- DOI を Crossref で引き、題・著者・年を照らす（D01 で、wiki の Bott の DOI が別の論文を指していた）。
- 日本語版・英語版・プレゼン版・evidence の表から、件数と提唱者の欄を抜き出して比べる（D01 で、「強い」の件数が四つの版で違っていた）。
- 公開文に、退ける語と LLM の記号（Phase・S60・安全弁・温度帯・Colophon・統合・完全に・最も）が無いかを grep する。
- 退ける語（統合・超え・一つにな・最適・正解・地図・融合・棄却される誤差・Function/Openness）と、英訳の揺れ（Edge と Relation）を、cs と wiki の公開ファイルで grep する。
- 5段階の文言が、決めた定義の表と一字ずつ同じかを見る。
- wiki の frontmatter を見る：repo の値が cs・pd・ks・as か、`status` が決まった語か、manifest_id が manifest にあって重複が無いか。
- git に入っていないパスへのリンク（`cs/knowledge/raw/` など）を見つける。
- 精読ノートの引用文が、PDF の本文（pdftotext）にあるかをページつきで見る。

機械でできないこと：当てはめがこじつけかどうか、数学や物理の記述が正しいか、帰属の微妙な違い、文体が規約に沿っているか。

### 記録の品質の点検（レビュー時の決まり）

計画のときの決まりだけでは、あとでレビューするときにどこを見ればよいか分からなくなる（pjdhiro 2026-11-08「最後にレビューできないでしょう。品質のルールがないと。どこをチェックしていいのかもわからなくなる。計画時のルールもだけど、レビュー時のルールもテストを作っていかないとね」）。記録の品質は、機械で見るものと人の目で見るものに分け、どちらも分野ごとに回す。

機械で見る（`scripts/check-cs-evidence.mjs`。`scripts/check.sh` に入っていて、commit の前と CI で回る。2026-11-08）：

1. `cs/evidence/reviewed.json` の各行：id の形、file が実在、reviewed が日付。en（英語の記録）があれば `en/<file>` で実在。
2. frontmatter：`file_id`（EV-Dxx）・`domain_id`・`title`・`last_updated`・`status`・`source_archive`（実在）。
3. 冒頭に文責が Claude であること。「## 一面の表」があること。
4. 一面の表の見出しに 論・対立・衝突・統合・照合の状態 があり、各行の照合の状態が `sources.md` §3 の四つのどれか。「精読ノートのみ」は「二次資料のみ（精読ノート）」と書く。
5. 「判定」の列は、一致・言い過ぎ・取り違え・帰属違い・付け足し・抜け・未判定 のどれかで始まる。
6. 論ごとの節に照合の状態の語があり、本文・要旨照合済と書く節には確かめ先（DOI・URL・manifest の行）がある。
7. （2026-11-09 に外した）記録が引く台帳の行が台帳にあるか。本文に台帳の番号を書かなくなったので、10 に替えた。
8. 手元の絶対パスが無い。旧い判定の語（verified・accepted・Accept など）を状態や判定の欄に使っていない。
9. 地の文の文末が「です・ます」（箇条書き・表・引用は見ない。だ・である が 2 割を超えたら落ちる）。
10. 本文（frontmatter・リンクの行き先・URL を除く）に、分野と原典の記号（D01・D30-S12 など）と、repo のパスやファイル名（pjdhiro/assets/…・cs/knowledge/…・docs/…・*.md など）が無い。公開文に記号を出さない決まり（writing §6-3・§6-5）を機械で止める（corrections の型 R の繰り返し。pjdhiro 2026-11-09「D とかの記号を公開ページには出さないルールだけど、やってないよね？」）。本文では、分野の名前と、著者・年・題で書き、台帳との対応は「台帳の「著者 年」の行」と書く。
11. 一面の表の各行の照合の状態に「本文照合済」がある。本文を読めなかった論は表に置かず、表の下と、論ごとの節の最後の「本文を読めなかった論」に分ける（「規約で決めたこと」の J11 の行。2026-11-10）。関わる実験の論文や別の著者の要約だけを読めた論は、機械では見分けられないので人が見る。

人の目で見る（司令塔が分野ごとに。エージェントの報告をうのみにしない）：

- 一面の表の対立・衝突・統合は、原典に書いてあることか。原典に無い対立を補って作っていないか。Claude の読み替えは、そう書いてあるか。
- 統合に至らない形を、過程の外（「失敗」「対象外」）に置かず、行として並べているか。片方の勝利・悪い統合・そのほかの至らない形の区別があるか。
- 出典を主張と同じ向きに当てているか（Gersick を裏付けに数える型）。「最も」「正確に一致」「三条件」のような言い過ぎが残っていないか。
- 要の点を二つ三つ確かめ直したか（DOI を Crossref で、原典の頁を pdftotext で、精読ノートの直しの元の行を）。エージェントが挙げた機械的な誤りは、確かめたものだけ直したか。
- pjdhiro の見方を本文に引いていないか（writing §7-5）。欠損・抱持の語を持ち込んでいないか。
- 重なる理論は、済んだ分野の記録を参照しているか。
- 文は writing.md（教科書のような普通の文・演出しない・断定しない・一文に一つ）か。

いつ：分野ごとに司令塔が両方を回す。5 分野ごとに記録の形を pjdhiro に見せる。30 分野のあと、段 3 に入る前に、全記録を機械の点検に通し、人の目の項目で一巡する。

作りたいもの（まだ無い）：引用した英文が原典の本文（pdftotext）にあるかの照合。DOI を Crossref で引いて題・年を照らす機械の点検。版（ja・en・pres）の件数と対応段階の欄を抜き出して比べる。
