# Love駆動開発は事業構想学のどこにあるか——構想・意図の手前の駆動源と、そこから生まれる過程

> LLM との対話録。要点を圧縮・再構成してあるが、話者（**私**＝pjdhiro ／ **Claude**）は明示する。参照用。
> 四候補の整理・狭め方・文案は **Claude の仮案**で、確定ではない。**私** の発言は、できるだけ元の言い回しを保つ。
> 用途：「プロジェクトデザインとは？」「Love駆動開発とは？」への回答の部品（pjdhiro「記録して」）。

## 0. 経緯（この対話の位置）

**私**：事業構想学とは？への回答として、一旦英訳であるプロジェクトデザインと置き、それへの回答として、一旦、Love駆動開発という概念に到達した。イコールでもあるし、一つの視点、見方、構え、現象の構造を説明しているように思う。事業構想学において、Love駆動開発とはどういう位置付けか。それを考えたい。

**Claude** の注：置き換えの連鎖（事業構想学 → プロジェクトデザイン → Love駆動開発）は、それぞれが前の問いへの「一旦の答え」で、答えが次の問いになっている。Love駆動開発は連鎖の最新の答えであって、最終の答えとは限らない。

## 1. 三つの言葉が答えている問いを分ける（Claude の仮案）

| 言葉 | 答えている問い | 起点 |
|---|---|---|
| 事業構想学 | 事業はどう構想され、計画され、実行されるか | 構想（構想する人の意図はすでに在るものとして扱う） |
| プロジェクトデザイン | その進め方そのものをどう設計するか | 手法を選ぶのでなく手法を対象化する（一段メタ）。ここで Doing に Being が加わった |
| Love駆動開発 | そもそも何が動かしているのか | 構想より前。人が集まり縁が生まれて動き出す、その駆動源 |

- この分け方では Love駆動開発は事業構想学の**上流・下地**。構想学は「構想がある」ところから始まるが、Love駆動開発は「なぜ構想が生まれ、なぜ人がそこに引き寄せられるか」を名指す。gravity-love の像で言えば、構想学や PMBOK が記述するのは軌道で、Love は軌道を回らせている中心。
- pjdhiro の挙げた三つの関係（イコール／視点・構え／現象の構造）は矛盾せず同時に成り立つ：中心なしに軌道はないという意味でイコール、Being 側から見る構えの名前という意味で視点、引力→縁→集まり→動くという機構の記述という意味で構造の説明。
- 事業構想学は実在する分野（構想力を鍛え、構想から計画へ降ろす体系）。その体系に置くと「構想の手前」が空席になっていることが見える。構想学は構想者の意図を前提にするので、意図がどこから来るかは問わない。Love駆動開発はその空席を埋める候補。gravity-love で未解明として残した「存在についての役割」は、この空席と同じ問題。

## 2. 構造か、視点か、原理か、デザインプロセスか

**私**：プロジェクトの構造を言ってるのか、プロジェクトを眺める視点なのか、プロジェクトがなぜ生まれ動くのかの原理のことなのか、デザインプロセスを言ってるのか。

**Claude** の整理：四つは競合する選択肢でなく、同じものに向けた四つの別の問い。芯は hero の文言「Love駆動開発と呼びたい**現象**」＝選んだ視点でも作ったプロセスでもなく、何度も遭遇した出来事に付けた名前。四候補はその現象への問いの違い：

| 候補 | 現象との関係 | 備考 |
|---|---|---|
| 原理（なぜ生まれ動くか） | 現象の**説明**。引力が縁を生み、縁が集まりを生み、集まりが動く | 一番芯に近い。gravity-love はこの層 |
| 構造（プロジェクトとは何か） | 現象が示唆する**帰結**。引力で動くなら Doing だけでなく Being を含む出来事だと言わざるを得ない | Love駆動開発そのものでなく、認めた結果の定義 |
| 視点（どう眺めるか） | 現象を見ようとする人の**構え**。「この集まりの引力はどこか」と問う目 | 現象は視点より先。見方を変えたから起きたのでなく、起きていたから見方が要った |
| デザインプロセス（どう進めるか） | 現象を受け入れた人が「ではどうするか」に答えたとき初めて現れる | 感情処理・欠損駆動思考はこの層の部品候補。手順としては未記述 |

- **名前の形の引っかかり**：「〇〇駆動開発」はテスト駆動開発・ドメイン駆動設計と同じ文法で、あれらはプロセスの名前。名前はプロセスを指す形なのに、中身は現象と原理に寄っている。「どれなのか」の迷いはこのずれが原因ではないか。
- ずれの扱いは二通り：現象の名前のままにするなら「開発」は少し言い過ぎで原理が中心と明言する／プロセスにまで育てるなら「引力に逆らわずに進めるとは具体的に何をするか」の手順をこれから書く（まだ空いていて、急いで埋める必要はない）。

## 3. 構想・意図・目的の手前、と「過程」

**私**：構想、そこに内包される意図や目的などの前に、か。「Love駆動開発は、事業構想学が前提として問わずに済ませている駆動源と、それによって生まれる過程を名指すもの」。後半の過程のところは。

**Claude**：はい、構想より前、そこに含まれる意図や目的よりも前。意図や目的は引力が言葉になった姿で、引力そのものではない。「過程」は入れたほうが正確になる。理由は二つ：

1. **名前の「開発」がそこに乗る**。「開発」をデザインプロセス（人が選んで踏む手順）でなく**引力から生まれて進んでいく経過**と読めば、§2 のずれは消える。テスト駆動開発の「開発」は手順だが、Love駆動開発の「開発」は、縁が集まりを生み、集まりが動き、動いた先で何かができていく成り行き。駆動源だけなら「Love」で足りて「開発」は要らない。「開発」が付いているのは、源とその成り行きを一語で言おうとしているから。
2. **過程を入れると構想の位置が変わる**。駆動源だけなら構想学は「その先」で直列（引力→構想→計画→実行）。過程まで含めると、構想・意図・目的はこの過程の**途中で結晶するもの**になる。引力で集まった人たちの中で、ある時点で「これをやりたい」が言葉になる。それが構想。構想は過程の入口でなく産物の一つで、最終産物でもない。構想のあとも引力は働き続け、計画や実行の下でも過程は進む。

- 構想学が記述するのは意図を起点にした Doing の列（構想・計画・実行）。Love駆動開発が名指すのは引力を起点にした Being の経過（縁・集まり・動き・そこで起きる感情・欠損・間主観性）。二つは前後の関係でなく、**同じ出来事を走る二本の過程**で、構想学の列は Being の経過の上に乗っている。index.html の「Doing と Being を包含する出来事」はこの二本のこと。
- 文案（Claude）：「Love駆動開発は、事業構想学が前提として問わずに済ませている駆動源と、その駆動源から生まれて構想・計画・実行の下を走り続ける過程を名指すもの」。総論に書くなら「駆動源と、そこから生まれる過程」で止め、中身は次の段落へ。
- 保留：「過程」は一方向に聞こえるが、引力は戻りも生む（離れる・ほどける・集まり直す）。往復まで含めるかは未決。

## 4. 経営学の列と争わない——「前段の駆動源を見つけた」

**私**：経営学でしょうね。一般の。私は前段の駆動源を見つけた。そんなとこかな。

**Claude**：構想・計画・実行の列は構想学に限らず経営学一般がすでに持っているもので、付け足すものはなく、付け足す必要もない。「前段の駆動源を見つけた」で主張の大きさがちょうどよい。経営学の列を書き換えるのでなく、その列が「意図がある」ところから始めていることに気づいて、意図の手前にあるものに名前を付けた。経営学と争わないし、要らないとも言わない。

- 見つけたものは二つで、固さが違う：**「駆動源がある」という事実**（経験から来ている・固い）と、**「それは引力の形をしている」という見立て**（gravity-love の構造類似・見方の一つ）。総論ではこの固さの差が伝わる書き方を。
- 過程のほうは「経営学の列の下でも引力が働き続けている」程度にとどめれば、「開発」の語も無理なく収まる。

## 5. 広がりすぎの自覚と狭め方——「人を集める引力」に限る

**私**：人間の原理を見つけに行ってるような広さになっちゃってますよね。構想という言葉の広さがそうさせてるのでしょうが。

**Claude**：なっている。広がった場所は「意図の前」と言った瞬間。意図の手前を問うと相手は「人はなぜ何かをするのか」になり、心理学・哲学が何百年もやっている問いになる。構想は一人の人間の行為を指すので、その手前を問えば自然に人間一般の原理に向かう。

- ただし見つけた現象はそこではない。経験したのは「人が集まって、何かが動いた」＝一人の中で意図が生まれる話でなく、**複数の人の間で起きる話**。重力の比喩も一つの物体でなく複数の物体が互いに回る話。
- **狭め方**：問いを「意図の前に何があるか」でなく「**共通の意図がまだ無いのに、なぜ人が集まるか**」にする。前者は人間の原理、後者はプロジェクトの範囲に収まる。駆動源は個人の動機でなく人と人の間の引力。経営学の隣（組織・集団）に置けて、心理学の下まで掘りに行かなくて済む。
- 広い版は捨てず置き場所を分ける：「引力一般」「関係が先にある存在論」は techo で育てる（既定）。pd 総論ではプロジェクトの範囲で「人を集める引力」だけを言い、広い版はそこを指す一行で済ませる。
- 言葉：総論で「構想の前」と言わず「**構想する人が揃う前**」と言えば広さは抑えられる。言葉を変えるだけで範囲が変わる、は pjdhiro の指摘どおり。

## 6. 言い直し——「私というアプリをリファクタリングしたら」

**私**：この対話の内容は、プロジェクトデザインとは？Love駆動開発とは？への回答の部品になるので記録して。**私はプロジェクトデザイナーとして、私を分析したのであり、それを喩えるなら、私というアプリをリファクタリングしたら Love駆動開発というタイトルが相応しい構造とプロセスだった、とも言えます。**

**Claude** の注（第一稿・一部を後で訂正）：この一文で §2 の「どれなのか」に別の角度から答えが出る。**構造とプロセスの両方**で、外から定義したものでなく、プロジェクトデザイナーである本人を分析対象にして取り出したもの。§5 の狭め方とも整合する：分析対象が「私」という一つのアプリなので人間一般の原理ではない。ただし「私」は複数の人の間にいる人なので、構造の中に「人と人の間の引力」が含まれる。「プロジェクトデザインとは？」への部品：プロジェクトデザイナーが自分自身を対象化する行為そのものが、プロジェクトデザイン（手法を対象化して設計する）の一例。〔この稿で「リファクタリングは振る舞いを変えない」と書いたのは誤り。下で訂正〕

**私**（続き）：もちろんリファクタリングあるあるで、バグ見つけちゃって、修正したら玉突きで修正が起きちゃって、一部機能が変わる、というか洗練されていく。コーナーケースに強くなったり。

**私**（さらに）：デバッグというのが正しいのでしょうね。

**Claude**（この時点の読み・後で訂正）：出発点を「何かがおかしい」＝デバッグと読んだ。〔誤り。下の本人の言葉のとおり、出発点は可読性〕

**私**：デバッグしたかったわけではないのです。バグが見つかることはウェルカムでしたが。最初は、動いてるコードの可読性を高めたんだと思いますよ。シンプルで短いのだけど、本人にしかわからなかった。なので関数や変数の名称を中身を表すものに変え、他者が読めるようにしていった。それはリファクタリングのようなもののはずだったが、少しずつ修正したり、関数を切り分けたり、モジュール化することで他との接続が容易になったり、構造が明確になったり。そんなコードを書くのと似ています。アジャイルに。

**Claude** の注（まとめ直し・仮案）：pjdhiro の三つの発言を通して読むと、経緯の順序はこうなる。

1. **出発点は可読性**。コードは動いていた（シンプルで短い）。ただし本人にしか読めなかった。関数や変数に中身を表す名前を付け、他者が読めるようにする。これがリファクタリングのはずだった。
2. **バグは副産物で、歓迎された**。直したかったのでなく、名前を付けていく途中で見つかった。デバッグが目的だったわけではない。
3. **玉突きで構造が変わる**。少しずつ直し、関数を切り分け、モジュール化すると、他との接続が容易になり、構造が明確になった。一部の振る舞いは変わり、洗練され、コーナーケースに強くなった。
4. **アジャイルに**。計画して一度に組み替えたのでなく、小さく直しては動かすを繰り返した。

喩えを repo に当てると（仮）：名前を付ける＝「Love駆動開発と呼びたい現象」に名前を付けたこと自体がこれ（hero の「言語化しようとしています」）。他者が読める＝公開の読み物の動機。関数の切り分け・モジュール化＝pd・ks・as・cs に分かれたこと。他との接続が容易＝cs を部品として引用する原則、techo での横断。アジャイル＝hero の「書きながら考えています」。

この読みの含意：Love駆動開発という題名は、デバッグの結果でも設計の結果でもなく、**他者が読めるように名前を付け直していく作業の結果**として付いた。動いていたものに名前を付けたので、現象が先で名前が後（§2 の「呼びたい現象」と整合）。そして名前を付け直す動機が「他者が読めるように」だった点は、駆動源の話（人と人の間の引力）とは別の層にある本人の動機で、ここでは接続しない（一面ずつ）。

**私**（続き）：私がしてきたプロジェクトのやり方をモジュールに切り分けるリファクタリングのような、可読性を高めたり、構造をシンプルにしたり、相互の接続を明確にしたり。それが創造や意識といった切り分けになっていった。欠損駆動思考は上手く書けなくてあっちこっちいったり描き直したり。全く同じ振る舞いを記述したかったのに全然違うものを作っちゃった。そんな紆余曲折ですね。

**Claude** の注（仮案）：
- **対象が確定した**：アプリは「私」一般でなく「**私がしてきたプロジェクトのやり方**」。§5 の狭め方（人間一般の原理でなくプロジェクトの範囲）は、分析対象の側からも裏付けられる。
- **モジュールの切り分けが repo になった**：創造（cs）と意識（as）は、やり方を切り分けたら出てきたモジュール。欠損駆動思考（ks）は切り分けが難しく、あっちこっち行って描き直した。ks が最も書きにくかったのは、他の二つのように「やり方の一部」として切り出せるものでなく、やり方の下に敷かれている層だったからではないか（CN-026「虚軸に値があって認知上は 0」＝切り出そうとすると見えなくなる）。これは仮。
- **「同じ振る舞いを記述したかったのに全然違うものを作った」**：リファクタリングの定義（振る舞いを保つ）からの逸脱を本人が明示した。含意は二つ。①できあがった四つの論は、過去のやり方の忠実な記述ではなく、記述しようとして生まれた別物。だから Love駆動開発は「過去にやっていたことの名前」と「記述の過程で生まれたものの名前」の二重になる。②記述しようとしたら別のものができる、は cs の創造のモデル（場→波→縁→渦）がこの一年の作業そのものに起きたということ。これも仮で、ここでは繋がない（一面ずつ）。
- 「紆余曲折」は保持論点でなく、経緯の正直な記述として残す。総論で経緯を書くなら、整然とした設計でなく紆余曲折として書く（git の日付入りの軌跡がその証拠）。

**私**（続き）：リファクタリングやデバッグなど、コードをクリーンにしていくことで、できることに気づき、新たな機能の追加につながることがあります。そんな感じですね。私は私をメタ認知で分解し、関数を切り分けるようにモジュールとして切り分け、発達段階のようなリストにまとめたり、そのせいで処理速度が上がったり、認知限界を超えない範囲でメモリ上で扱える量が増え、結果的に扱える量が増えたことで広く扱えるようになった。そんな洗練というかバージョンアップもありました。分析だったはずなのに。これもよくあることですよね。

**Claude** の注（仮案）：よくあることで、コード側と認知側で同じ機構が働いている。
- **コード側**：クリーンにすると、できることが見える。理由は、追加のコストが下がる（接続が明確なので、どこに足せばよいかが分かる）のと、モジュールに名前が付くと「これとこれを組み合わせたら」という組み合わせが見えるから。機能追加はリファクタリングの目的ではないが、よく結果になる。
