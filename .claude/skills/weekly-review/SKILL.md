# 週のまとめのレビュー

2026-11-10 に一度回した形（Issue #111）から作った。読み物一本を main に出す前に念入りに見る手順は `docs/rules/review.md`、一枚の公開ページの点検はスキル `public-page-review`。ここは repo の全体を見るとき。指摘の中身はここに書かない（その回の Issue にある）。

## 役

- 司令塔は、このスキルを使う親のセッション。自分では直さない。
- **司令塔を二つに分ける。** レビューの司令塔は、二陣を出して Issue を作るところまで。直しの司令塔（新しいセッション）は、Issue と記録から始めて、直しを出す・確かめる・答えを渡す。2026-11-10 は一つのセッションで通し、長くなりすぎた。
- レビュー役は、読むだけのエージェント（Agent ツール・バックグラウンド）。モデルは、pjdhiro の指定が無ければ Opus（`docs/cs-review/README.md`「エージェントの分け方」）。同じ持ち場に二人を当てない。
- 2026-11-10 の数：20 人で約 500 万トークン、一人 8〜23 分。回す前に、この大きさを pjdhiro に一行で伝える。

## 始める前に

1. `CLAUDE.md` の表のとおりに規約を読み、`bash scripts/session-digest.sh` で記録の要点を読む。
2. `bash scripts/sync-develop.sh` を単独で回し、worktree を develop にそろえる（2026-11-10 は 26 commit 古いまま始め、規約への写しと違和感帳の見張りができなかった）。
3. 報告の置き場を決める：scratchpad の下に `review/`。レビュー役が書くのはここだけ。
4. **頼む文を書く前に `where-to-look.md` を読む**（このスキルの下。どこを見ると見つかるか）。
5. `reviewer-common.md`（レビュー役への共通の決まり）の `{…}` を埋めて、報告の置き場に `00-common.md` として置く。頼む文は「先に 00-common.md を読む」＋持ち場の名前・見る範囲・見てほしい点、だけにする。場所は行番号でなく、見出しと鍵の文で書かせる（レビューの間も develop は動く）。

## 二段で進める

**第一陣**を一度に出す。持ち場（2026-11-10 は 11 人。次からは物理・数学を足す）：

- 規約の整合／ハーネスと仕組み／今週の記録の棚卸し／計画と内部の文書
- その週にいちばん直された読み物を四つに分ける：前半／後半／文脈ゼロの読解／事実の照合
- 入口（四つのトップ）／ほかの読み物（広く浅く）／公開の範囲と安全
- 物理・数学の正確さ（読み物に物理のたとえがあるとき。`where-to-look.md` の 5）

**第二陣**は、返った報告の頭の「見ていないところ」から決める。pjdhiro に「ゆるいところ」を聞かれる前に、司令塔が自分で並べる。2026-11-10 の持ち場（9 人）：引用の出所の全件／読み物の通読（第一陣が浅く見たもの）／物理の正確さ／公開に出ている内部の文書の全件／サイトの奥（as・ks・cs の下のページ）／wiki の抜き取りの照合／計画とスキルの本文／調査の記録の出典の全件。

走っているレビュー役に関わる pjdhiro の判断が途中で出たら、すぐそのレビュー役に伝える。

## レビューの司令塔がすること

- **画面を見る**：3001 で、公開ページをスマートフォンの幅で開き、はみ出しと、表の横の動きを測る。畳みは開いた状態でも測る（2026-11-10 は、閉じた畳みの中を測れなかった）。レビュー役は画面を見ない。
- **重い指摘の要を、自分で開いて確かめる。** 報告は証明ではない。鍵の文を今の develop で引き直し、確かめたものに【確】を付ける。
- **中身を開かずに、重さを pjdhiro に伝えない**（型 K の K0。2026-11-10 は、書庫の中身を開かずに「公開してはいけない」と伝えた）。
- **範囲・看板・目標に関わる指摘は、直しに回さず、聞くものに置く。** レビュー役の指摘そのものが、本人の射程を狭めていることがある。回す前に `stance.md` で見る（2026-11-10：「入口が〜につながっていない」の形の指摘二つを確かめずに頼む文に書き、入口に入れてから戻した。型 C。本人の言葉は `stance.md` 2-4 の、pd と as の入口の行）。
- **独立に重なった指摘を先に。** 二人以上が別々に指したものは信頼できた。
- **一つの Issue にまとめる**（pjdhiro 2026-11-10「このレビューの指摘事項は一つの issue として修正していきたい」）。高と、重なったものを、直す単位（束）に並べる。中・低は報告に置いたままでよい。Issue に、報告の置き場と【確】の読み方を書く。
- **報告を、本体の `.cache/session/review-YYYYMMDD/` に写す。** scratchpad はセッションと一緒に消える。本体へは Write ツールでは書けないので、`cp` で写す。
- ここで区切り、記録に引き継ぎを書く。

## 直しの司令塔がすること

- **持ち場は、束（指摘の種類）でなく、ページ（ファイル）で分ける。** 同じファイルを二つのセッションが直さない。`docs/rules/` を直すセッションは一つにし、ほかは「規約に写すもの」を Issue のコメントに書く。共通の決まりは `fix-common.md` を埋めて渡す。出す順は、機械的な誤り → 規約と仕組み → 判断の済んだもの → ページごとの束。
- **main へ送るのは、一つのセッションにまとめる。** 同時に走る直しのセッションは、ほかのセッションの記録に「main には送っていない」があると、送る前の確かめ（`publish-main.sh`）で止まる（2026-11-10）。途中の状態（しまったページへの行が入口に残る など）では送らない。
- **聞くページは、一つの一覧にして pjdhiro に渡す**（2026-11-10 は五つに分かれた）。選ぶだけの問いは、最初から押せるボタンにする。定義についての問いは「どちらで書くか」の二択にせず、本人の言葉そのままを候補に並べ、いくつ選んでもよい形にする（型 B）。聞く前に、答えの予想を記録に書く。答えを受けたページに、問いを足して出し直さない（`stance.md` 2-8）。規約から答えが出るものは、聞かずに決め、誰が決めたかを `decisions.md` に書く。
- **pjdhiro が「回答した」と言ったら、ページのデータベース（`answers`）とコメントの両方を、一度に全部読む。** 「Claude に送る」が押されていないコメントも答え。
- **直しが返ったら、突き合わせる。** 頼んだ問いの数と、作られたページの問いの数（2026-11-10 は、頼んだのに作られなかった問いが残った）。一つのセッションに続けて頼んだときは、前の頼みが済んだかを Issue のコメントで。要は自分で確かめる（`bash scripts/check.sh` の終了コード・鍵の語が 0 になったか・3001）。
- **量の多い束（読めていない出典・wiki の作り直し）は、一回で終わらない。** 終わらなかった分を、ページごとの残りの表で Issue に残させる。pjdhiro の手が要るもの（ブラウザでの保存）は、開く URL・保存する名前・何を確かめるかを一件ずつ。
- 済んだ聞くページは、答えが md に写っているのを見てから消す。

## 道具の癖

- 文脈ゼロの読解：`node pd/scripts/reader-llm-comprehension-test.mjs <ページの名前> --out <報告の置き場の下>`。引数はファイルのパスでなくページの名前（名前の一覧はスクリプトの頭）。`--out` を付けないと repo の中（`pd/.cache/active/`）に書く。
- 日本語のファイル名は `git ls-files | grep` で数えると少なく出る。`git ls-files -z` か `find` で数え直す。

## セッションの終わりに

`CLAUDE.md` の「セッションの終わりに」を行う。記録には、したこと・回して分かったこと・聞く前の予想と答えの表・残した束を書く。回して分かったことは、同じセッションで、このスキルの四つのファイルに日付を付けて足す。足す前に、既にある行に溶かせるかを見る。観点は `where-to-look.md`、進め方はこの文書、レビュー役と直しのセッションに守らせることは二つの雛形に置き、同じ決まりを二か所に書かない。
