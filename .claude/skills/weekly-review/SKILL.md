# 週のまとめのレビュー

2026-11-10 に一度回した形（Issue #111）から作った。読み物一本を main に出す前に念入りに見る手順は `docs/rules/review.md`。ここは repo の全体を見るとき。指摘の中身はここに書かない（その回の Issue にある）。

## 役

- 司令塔は、このスキルを使う親のセッション。自分では直さない。レビュー役を出し、報告を確かめ、Issue にまとめ、直しを別のセッションへ出す。
- レビュー役は、読むだけのエージェント（Agent ツール・バックグラウンド）。モデルは、pjdhiro の指定が無ければ Opus（`docs/cs-review/README.md`「エージェントの分け方」）。同じ持ち場に二人を当てない。
- 2026-11-10 の数：20 人で約 500 万トークン、一人 8〜23 分。回す前に、この大きさを pjdhiro に一行で伝える。

## 始める前に

1. `CLAUDE.md` の表のとおりに規約を読み、`bash scripts/session-digest.sh` で記録の要点を読む。
2. `bash scripts/sync-develop.sh` を単独で回し、worktree を develop にそろえる（2026-11-10 は 26 commit 古いまま始め、規約への写しと違和感帳の見張りができなかった）。
3. 報告の置き場を決める：scratchpad の下に `review/`。レビュー役が書くのはここだけ。
4. `reviewer-common.md`（このスキルの下。レビュー役への共通の決まり）の `{…}` を埋めて、報告の置き場に `00-common.md` として置く。頼む文は「先に 00-common.md を読む」＋持ち場の名前・見る範囲・見てほしい点、だけにする。場所は行番号でなく、見出しと鍵の文で書かせる（レビューの間も develop は動く）。

## 二段で進める

**第一陣**を一度に出す。持ち場（2026-11-10 は 11 人）：

- 規約の整合（`CLAUDE.md`・`docs/rules/` の食い違い・古い行・毎回読む分の大きさ）
- ハーネスと仕組み（`.claude/`・`scripts/`・`.githooks/`・`.github/`。書いてある仕組みが実際に動くか）
- 今週の記録の棚卸し（`.cache/session/`。答えが来ないまま閉じた問い・ずれ・繰り返し）
- 計画と内部の文書（`docs/` の計画、`pd/`・`cs/`・`ks/`・`as/` の下の内部の文書）
- その週にいちばん直された読み物を四つに分ける：前半／後半／文脈ゼロの読解／事実の照合
- 入口（四つのトップ）
- ほかの読み物（広く浅く）
- 公開の範囲と安全（Pages に何が出ているか・公開してはいけないものの混入）

**第二陣**は、返った報告の頭の「見ていないところ」から決める。pjdhiro に「ゆるいところ」を聞かれる前に、司令塔が自分で並べる。2026-11-10 の持ち場（9 人）：引用の出所の全件／読み物の通読（第一陣が浅く見たもの）／物理の正確さ／公開に出ている内部の文書の全件／サイトの奥（as・ks・cs の下のページ）／wiki の抜き取りの照合／計画とスキルの本文（エージェントが読んで動く文書）／調査の記録の出典の全件。

## 司令塔がすること

- **画面を見る**：3001 で、公開ページをスマートフォンの幅で開き、はみ出しと、開いた表の横の動きを測る。レビュー役は画面を見ない。
- **重い指摘の要を、自分で開いて確かめる。** 報告は証明ではない。鍵の文を今の develop で引き直し、確かめたものに【確】を付ける。付けていないものは、直すセッションに確かめさせる。
- **中身を開かずに、重さを pjdhiro に伝えない。** 2026-11-10 は、書庫の中身を開かずに「公開してはいけない」と伝え、「危険なファイルではないよ。論文調査の結果でしょ。」と言われた（型 K の K0）。
- **独立に重なった指摘を先に。** 二人以上が別々に指したものは信頼できた。
- **点検が通ることと、決まりが守られていることを分けて読む。** 点検の 0 件は、誤りが無い意味でない。
- **一つの Issue にまとめる**（pjdhiro 2026-11-10「このレビューの指摘事項は一つの issue として修正していきたい」）。高と、重なったものを、直す単位（束）に並べる。中・低は報告に置いたままでよい。Issue に、報告の置き場と【確】の読み方を書く。
- **報告を、本体の `.cache/session/review-YYYYMMDD/` に写す。** scratchpad はセッションと一緒に消える。本体へは Write ツールでは書けない（アプリの仕組みが止める）ので、`cp` で写す。
- **判断が要る問いは、一つのページ（アーティファクト）にまとめる。** 選ぶだけの問いは、最初から押せるボタンにする。問いの前に、何の作業で、選ぶと何が変わるかを、例を一つ添えて書く。聞く前に、答えの予想をセッションの記録に書く。答えを受けたページに、問いを足して出し直さない（`stance.md` 2-8・型 P・型 G）。規約から答えが出るものは、聞かずに決め、誰が決めたかを `decisions.md` に書く。
- **直しは、ページごとに分けて別のセッションへ出す。** 同じファイルを二つのセッションが直さない。`docs/rules/` を直すセッションは一つにし、ほかのセッションは「規約に写すもの」を Issue のコメントに書く。直しのセッションへの共通の決まりは `fix-common.md`（このスキルの下）を埋めて渡す。出す順は、機械的な誤り → 規約と仕組み → 判断の済んだもの → ページごとの束。
- 直しが返ったら、要を自分で確かめる（`bash scripts/check.sh` の終了コード・鍵の語が 0 になったか・3001）。確かめが済んだら、`CLAUDE.md` の Git の節のとおりに main へ送る。

## 道具の癖

- 文脈ゼロの読解：`node pd/scripts/reader-llm-comprehension-test.mjs <ページの名前> --out <報告の置き場の下>`。引数はファイルのパスでなくページの名前（`love-driven-dev` など。名前の一覧はスクリプトの頭）。`--out` を付けないと repo の中（`pd/.cache/active/`）に書く。
- 日本語のファイル名は `git ls-files | grep` で数えると少なく出る。`git ls-files -z` か `find` で数え直す。
- レビュー役が Issue を読むために `gh` をサンドボックスの外で走らせたことがある。外へ出る命令の扱いは `reviewer-common.md` に書いてある。

## セッションの終わりに
